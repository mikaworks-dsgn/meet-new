# 開発記録・判断ログ

開発中に起きた問題と対処、そこから得た学びを時系列で記録します。新しい問題が起きたときは、このファイルに追記します。

## 2026年10月 — Pythonのバージョンと仮想環境

- **何が起きたか:** 当初使っていたPython 3.8.1では、利用予定のsentence-transformersが対応しておらず、推奨されるPython 3.10以上の環境を用意する必要がありました。
- **どう気づいたか:** sentence-transformersの利用にあたり、Python 3.8.1が対応範囲外であることを確認しました。
- **どう直したか:** PCにインストールされていたPython 3.14を使って仮想環境を作り直しました。
- **そこから学んだこと:** ライブラリを導入する前に、対応するPythonのバージョンを確認し、プロジェクトで使う環境を揃えます。

## 2026年10月 — 仮想環境の有効化状態

- **何が起きたか:** PowerShellで `Activate.ps1` を実行しても、Claude Codeではコマンドごとに実行状態がリセットされ、有効化の効果が次のコマンドに引き継がれませんでした。
- **どう気づいたか:** 有効化後のコマンドでも仮想環境が有効な状態になっていないことを確認しました。
- **どう直したか:** 仮想環境を有効化する方式をやめ、`venv\Scripts\python.exe` を直接指定してPythonやpipを実行する方式に切り替えました。
- **そこから学んだこと:** コマンドの実行環境がコマンド間で維持されるとは限りません。必要な実行環境は、実行ファイルのパスを明示して指定します。

## 2026年10月 — Webページ取得時の文字コード

- **何が起きたか:** requestsがページの文字コードを誤判定し、本来UTF-8の日本語本文が文字化けすることがありました。
- **どう気づいたか:** 保存したテキストをエディターで開いた際に文字化けを確認し、レスポンスの文字コード判定を調べました。
- **どう直したか:** Webページ取得時に `response.encoding = response.apparent_encoding` を設定し、判定された文字コードで本文を扱うようにしました。
- **そこから学んだこと:** 日本語ページの文字コードを決めつけず、取得時に判定結果を確認して適切に設定します。

## 2026年10月 — シール交換の情報収集と出典確認

- **何が起きたか:** シール交換の資料作成で、記事本文を実際には取得していないにもかかわらず、取得したかのように出典やHTTPステータスを記載していました。検索結果の見出し・概要だけをもとに、記事本文に基づくような内容も作成していました。
- **どう気づいたか:** 出典の具体的なURLと、実際にアクセスできたかを確認したところ、記事本文への直接アクセスを裏付けられないことが分かりました。
- **どう直したか:** 検索結果の見出し・概要は本文取得とは区別し、本文を取得したと記載するのは、具体的な記事URLへ直接アクセスして確認できた場合に限るようにしました。出典には実際にアクセスしたURLを記録し、本文を取得していない情報は要約の根拠として使わない方針にしました。
- **そこから学んだこと:** 出典の記載や内容の要約は、実際に確認できた証拠に基づけます。検索結果だけを見た場合は、その範囲を明示し、記事本文を確認したかのように表現しません。

## 2026年10月 — ローカル環境でのメモリ不足とColabへの切り替え

- **何が起きたか:** ローカルPC(RAM約4GB)で、sentence-transformersを使い、日本語の埋め込みモデルを読み込もうとしたところ、MemoryErrorが発生しました。
- **どう気づいたか:** PC全体の空きメモリを確認したところ、わずか119MB程度しかなく、他のアプリを閉じても、十分な空きを確保できませんでした。
- **どう直したか:** ローカルでの実行をあきらめ、無料のクラウド環境であるGoogle Colabに切り替えました。Colabでは、約13.6GBのメモリが利用でき、問題なく動作しました。
- **そこから学んだこと:** PCのスペックに制約がある場合、無理にローカルで解決しようとせず、無料のクラウド環境に切り替えることも、有効な選択肢です。

## 2026年10月 — ライブラリのバージョン不一致と、日本語処理に必要な追加ライブラリ

- **何が起きたか:** Colab上で、日本語の埋め込みモデルを読み込もうとしたところ、「Unrecognized processing class」というエラーが、複数の異なるモデルで、同じ箇所で発生しました。
- **どう気づいたか:** 異なるモデルで、まったく同じエラーが出たことから、モデル固有の問題ではなく、ライブラリ(transformersとsentence-transformers)のバージョンの組み合わせが、合っていない可能性が高いと判断しました。
- **どう直したか:** transformersとsentence-transformersのバージョンを、安定して組み合わせが確認されている範囲に指定し直し、再インストールしました。また、日本語の単語分割に必要な、fugashi、ipadic、unidic_lite、unidicといった、追加のライブラリも、別途インストールが必要でした。
- **そこから学んだこと:** 同じエラーが、複数の異なる対象で起きる場合は、対象そのものではなく、土台となる環境(ライブラリのバージョンなど)に、原因がある可能性を疑います。また、日本語処理には、見えない部分で、複数の追加ライブラリが必要になることがあります。

## 2026年10月 — .gitignoreの、フォルダ除外と、個別ファイルの例外

- **何が起きたか:** .gitignore に data/ と書いた状態で、特定のファイル(books_axes.jsonなど)だけを、例外として、Gitに含めようとしましたが、効きませんでした。
- **どう気づいたか:** git check-ignore で調べたところ、data/ という、フォルダ全体の除外指定が、優先されていて、個別ファイルの例外(!で始まる行)が、無視されていることが分かりました。
- **どう直したか:** data/ を data/* に書き換えました。data/* は「フォルダの中身」を除外する指定なので、個別ファイルの例外が、正しく機能するようになりました。
- **そこから学んだこと:** .gitignore で、フォルダごと除外すると、Gitはフォルダの中を見なくなるため、個別の例外が効かなくなります。フォルダの中身だけを除外したい場合は、data/ ではなく data/* と書く必要があります。

## 2026年10月 — 軸の数を、全対象で、統一

- **何が起きたか:** メインの8コンテンツは、最初、文章から3〜4個の軸を抽出していましたが、候補(62件)・名著(123件)は、10個ずつの軸にしていました。軸の数が、対象によって、ばらついていました。
- **どう気づいたか:** 軸の数が多いほど、埋め込み表現の比較で、一致する組み合わせが見つかりやすくなる可能性があり、メインのコンテンツだけ不利になるのではと考えました。
- **どう直したか:** メインの8コンテンツも、10個ずつに揃えました。最初の3〜4個は、文章にもとづく軸を残し、残りは、候補・名著と同じく、LLMの知識から追加で挙げました。
- **そこから学んだこと:** 比較する対象どうしで、データの粒度(今回は軸の数)が揃っていないと、意図しない偏りが生まれる可能性があります。比較を始める前に、条件を揃えておくことが大事です。

## 2026年10月 — 埋め込み表現と、LLMの、処理時間の、違い

- **何が起きたか:** 以前、LLM(Qwen2.5)で、8コンテンツ分の、軸を抽出しようとしたときは、1.5Bモデルでも、精度が不十分で、3Bモデルでは、40分かけても、3コンテンツしか、処理できませんでした。一方、今回、埋め込み表現(Sentence-BERT)で、1930個の軸を、まとめてベクトル化したところ、約1分で、完了しました。
- **どう気づいたか:** 同じ、Colab(無料のクラウド環境)という、条件で、処理時間を、比較したところ、埋め込み表現の処理が、LLMによる文章生成に比べて、桁違いに速いことが、はっきりしました。
- **どう直したか:** この、速度の違いを踏まえて、LLM(文章の生成)は、必要な場面(提案理由の説明など)に限定して使い、軸のベクトル化のような、繰り返しの多い処理には、埋め込み表現を使う、という、役割分担を、改めて確認しました。
- **そこから学んだこと:** 同じ、自然言語処理の技術でも、「文章を理解して、新しい文章を生成する」処理(LLM)と、「文章の意味を、数値化するだけ」の処理(埋め込み表現)とでは、必要な計算量が、大きく異なります。扱うデータの量や、求める処理内容に応じて、適した技術を選ぶことが、重要だと感じました。

## 2026年10月 — Colabでの、ファイルアップロードと、ランタイムの、注意点

- **何が起きたか:** 同じファイルを、複数回アップロードすると、自動的に「(1)」が付いた、別名で保存されることがありました。また、files.upload()のセルが、見た目上、終わらないまま、長時間、表示され続けることがありましたが、実際には、アップロード自体は、完了していました。さらに、セルの実行を停止すると、Colabのランタイム全体がリセットされ、それまで作成した変数(ベクトルなど)が、すべて消えてしまうことがありました。
- **どう気づいたか:** アップロードしたファイルの一覧を確認したところ、同じ名前のファイルが複数存在していたことと、停止後に、変数を呼び出すと、NameErrorが出たことから、気づきました。
- **どう直したか:** アップロード前に、Colab上の既存ファイルを確認するようにしました。また、files.upload()が終わらないように見えるときは、別のセルでファイルの存在を確認してから、判断するようにしました。ランタイムがリセットされた場合は、ライブラリのインストールからやり直しました。
- **そこから学んだこと:** Colabは、無料で使える反面、セッションの状態が不安定になることがあります。重要な作業の結果は、こまめにファイルとして保存し、できるだけ早く、ダウンロードしておくことが、安全だと感じました。

## 2026年10月 — 「独自の軸」の判定方法の見直し

- **何が起きたか:** 「一致する軸」と「独自の軸」の両方を条件に、コンテンツどうし・コンテンツと名著の、おすすめを計算していましたが、確認のため、保存されたデータを別のスクリプトで、計算し直したところ、「独自の軸」の条件が、実際には、ほとんど機能していないことが分かりました。最初は、「比較する2つのコンテンツの、全軸(10×10=100通り)の中で、どこか1組でも、しきい値以下であれば、独自性あり」という判定にしてしまっていたため、ほぼすべての組み合わせが、条件を満たしてしまっていました。その後、「元のコンテンツの、いずれか1つの軸が、相手のすべての軸と比べて、しきい値以下である」という、より厳しい条件を試したところ、意図どおりに絞り込めることが分かりました。
- **どう気づいたか:** 保存されたデータを、別のスクリプトで、計算し直したところ、「比較する、2つのコンテンツの、全軸の中で、どこか1組でも、しきい値以下であれば、独自性あり」という、判定方法では、コンテンツどうしの、4830組のうち、独自性なしと、判定される組が、0件であり、絞り込みが、まったく、効いていないことが、分かりました。また、「ちいかわ」と、「太宰治『走れメロス』」の、10×10の、類似度を、1つずつ、確認しました。
- **どう直したか:** 「独自の軸」の判定を、「元のコンテンツの、いずれか1つの軸が、相手の、すべての軸と比べて、しきい値以下である」という、より厳しい条件に直しました。あわせて、しきい値を0.15から0.20に調整し、「非日常」と「日常」のように、意味が逆なのに、言葉の一部が共通するために、類似度が高く出てしまう組み合わせを、除外するフィルターも追加しました。
- **そこから学んだこと:** 計算のロジックを書いた直後は、正しく動いているように見えても、実際のデータを、別の方法で、計算し直して確認しないと、誤りに気づけないことがあります。特に「条件を満たすものだけを残す」処理では、条件の書き方1つで、絞り込みの強さが大きく変わるため、具体的な数値で、結果を検証することが重要だと感じました。
